# RealCLIP D: an independent framework with two Luna agents

D proposes morphological hypotheses from compound knowledge, then observes Cell Painting images with CellProfiler (CP) support to generate English descriptions. Its final text pairs one treatment well's multi-site, multi-channel image collection with one short visual description.
It is an independent Python project: dependencies, configuration, prompts, tests, caches, and run directories all live inside D. It does not import implementations or results from other approaches.
The project includes the framework, synthetic demonstrations, and a separate three-compound research pilot. It does not include biological validation, bulk data generation, or CLIP training. Completion status, model outputs, and usage for a live pilot are recorded in that run's report.

## How the two agents work together

1. The **research agent** follows four steps: identify the compound; research and summarize its properties, mechanisms, and reported cellular effects; combine those findings with supplied MoA and experimental context to develop morphology hypotheses; and guide the observation agent on where to look, what visual changes to examine, and how to compare treatment with control. It cannot access images or CP.
2. The output follows the four research stages: compound identification, source findings and analysis, morphology hypotheses, and observation guidance. Each hypothesis explains source-reported observations separately from the agent's predictions, with applicability and uncertainty. Sources are recorded once. A separate observation view contains appearance, applicability, inspection locations, features, and treatment/control comparisons.
3. The **observation agent** receives the hypothesis view, experimental conditions, treatment/control images, and a CP query tool in a fresh context. Its internal modules run in order: **baseline → guided → writer → reviewer → summarize**. The first four produce a complete reviewed report and evidence records; the final Summarize module returns a short English `description` for the treatment well. It has no network tools, does not inherit the research conversation, and does not receive compound identifiers, MoA, or mechanistic facts.

There are two functional agents. Summarize is the last module inside Observation;
`run` and `describe` execute it automatically. Its text-only SDK call has no tools,
does not re-inspect images or query CP, and returns plain text without output
citations or an automatic correction call. See the [complete Observation module
flow](docs/OBSERVATION_MODULES.md) and [Summarize module](docs/summarize_module.md).

Both agents use `Agent` / `Runner` from the OpenAI Agents SDK with the Responses API. The configured model name is `gpt-6-luna`, with reasoning effort `high` by default.
Model selection and actual API availability are established by the account and the request/response records for each run.
Prompts are stored separately and versioned, allowing research and image-observation strategies to evolve independently.

See the [four-stage output guide](docs/RESEARCH_AGENT_V3.md), [exact JSON schema](docs/research_output_schema_v3.json), and [synthetic example](examples/research_v3_synthetic_example.json). Validation checks structure, authentic source references, and one guidance entry per hypothesis. It does not independently verify the model's scientific interpretation. The [historical V2 guide](docs/RESEARCH_AGENT_V2.md) describes the older evidence-classification checks for saved V2 results.

The [article-reading tool](docs/READ_ARTICLE.md) returns an overview, chosen sections,
or full-text pages. The agent chooses its reading scope from the complete outline;
article text is paginated in order without keyword filtering or silent clipping.

Use a new output directory for the complete five-module Observation workflow.
The reviewed four-module report remains a V4 artifact under
`observation/reviewed/`; the final `observation/result.json` is V5 and contains
the short `description` and the complete `full_description`. Existing saved
reports are not rewritten. Output contract versions and full retrieval metadata
are stored by the program rather than generated by the model.

The observation agent may reject hypotheses, preserve disagreement between fields of view, and record unexpected changes.
A CP measurement change without image evidence cannot count as visual confirmation. The program validates structure and references; these checks are distinct from a biological accuracy review.

The [reviewed Observation implementation](docs/OBSERVATION_AGENT.md) uses component
checks, partial hypothesis support, CP-assisted image review, and sentence-level
evidence mapping for research handoffs. The program joins exact reviewed sentences
into the complete report, then Summarize compresses that report into the final
description. The complete report retains its evidence; the final short description
has no per-sentence evidence output. Mock mode uses explicitly synthetic responses
and does not perform biological observation. The earlier
[workflow design](docs/OBSERVATION_AGENT_DESIGN.md) describes the research handoff;
the [current module flow](docs/OBSERVATION_MODULES.md) includes Summarize. Offline
tests do not validate biological accuracy or CLIP performance.

## Installation and quick start

Python 3.12 or 3.13 and [uv](https://docs.astral.sh/uv/) are required. Run these commands inside `D`:

```bash
uv sync --locked
uv run realclip-d validate --input examples/sample.json
uv run realclip-d run --input examples/sample.json --output runs/demo
uv run pytest
```

The default `mock` mode requires no API key or network access. It exercises Research and all five Observation modules through local SDK fixtures for development checks.
Everything in `examples/` is explicitly synthetic: fictional identities, geometric PNG images, and manually specified CP values. These examples cannot support scientific conclusions.

Run stages separately:

```bash
uv run realclip-d research --input examples/sample.json --output runs/research-only
uv run realclip-d describe --input examples/sample.json --research runs/demo/research/result.json --output runs/description-only
```

`research` stops after the Research Agent. Both `run` and `describe` finish with
the Summarize module automatically; neither requires a separate Summarize command.
Read the final text from `runs/demo/observation/description.txt` or the `description`
field in `runs/demo/observation/result.json`. The complete reviewed report is in
`runs/demo/observation/reviewed/result.json`.

Replay saved results without making new model or database requests:

```bash
uv run realclip-d run --input examples/sample.json --mode replay --replay-from runs/demo --output runs/replayed
```

Use `--config config.example.json` to select configuration explicitly. Without it, D uses its own defaults and does not search parent directories for configuration.
Each agent defaults to at most eight model turns. Observation's total includes
one reserved request for its final Summarize module; its five-module flow requires
at least five turns. Tool calls, web searches, request timeouts, and output token
limits are configurable.

`observation_summary_channels` defaults to `["DNA", "RNA", "ER", "Mito", "AGP"]`.
The workflow selects the available original treatment views in those channels,
across all supplied sites; control images and Brightfield are excluded by default.
Override this list explicitly in the configuration if the intended CLIP collection
uses different channels. Final encoder resizing and normalization remain a separate
training configuration.

## Preparing your own input

See `examples/sample.json` for a `SampleInput` JSON example. Relative image and CP paths resolve from the directory containing the input file.

| Field | Content |
|---|---|
| `sample_id` | A unique sample identifier containing only letters, digits, underscores, or hyphens |
| `compound` | At least one identifier: name, complete InChIKey, SMILES, PubChem CID, or ChEMBL ID |
| `known_moa` | A list of known MoA strings; use an empty list when none are available |
| `context` | Cell line, dose, treatment duration, and notes on experimental conditions; keep unknown conditions null |
| `images` | Each image's unique ID, path, treatment/control role, explicit well ID, channel, field of view, and image type |
| `cp_file` | Path to the CP CSV; `null` when CP is unavailable |

The number of images is flexible. Supply one explicitly identified treatment well
and its control images, with channels and fields of view identified. The full
Observation workflow checks the target well and selected treatment channels before
model calls. Different fields, overview images, and crops must not be interpreted
as before/after views of the same cell.
CP input must already be in long-table format with these column names:

```csv
feature_id,feature_name,compartment,channel,family,role,value,unit,scope
example_control,AreaShape_Area,Nuclei,DNA,AreaShape,control,50,pixel^2,well
example_treatment,AreaShape_Area,Nuclei,DNA,AreaShape,treatment,60,pixel^2,well
```

`feature_id` is used by observation references; give every record a unique ID. `role` is `treatment` or `control`. `scope` specifies the measurement extent, such as a whole well, field, or object.
The first version only reads explicitly supplied CSV files and queries them by compartment, channel, and measurement family. It does not run CellProfiler or introduce normalization.
A whole-well measurement cannot establish that a cell in a particular crop exhibits the change.

## Official tools and live runs

The research agent calls official HTTP APIs through local Python functions; the model does not connect directly to databases.
Tools return a common envelope containing status, data, source IDs, URLs, retrieval timestamps, and cache references. Raw database responses are saved in the run directory.

| Source | Official interface used |
|---|---|
| PubChem | [PUG-REST](https://pubchem.ncbi.nlm.nih.gov/docs/pug-rest) for identity, structure, and synonyms; [PUG-View](https://pubchem.ncbi.nlm.nih.gov/docs/pug-view) for pharmacology and other annotations with sources |
| ChEMBL | [Data Web Services](https://chembl.gitbook.io/chembl-interface-documentation/web-services) for molecules, mechanisms, activities, and linked experimental information, with pagination |
| Europe PMC | [REST API](https://europepmc.org/RestfulWebService) for paper searches, abstracts, and available full-text XML |
| Web | [OpenAI Web Search](https://developers.openai.com/api/docs/guides/tools-web-search), available only to the research agent for supplementary discovery |

PubChem defaults to at most two requests per second, using a limiter shared across its tools.
ChEMBL records exact molecules and parent relationships separately; a parent mechanism cannot automatically become direct evidence for the exact compound.
Ambiguous identities, missing records, unavailable interfaces, and rate limits have explicit statuses and are not disguised as an absence of relevant evidence.
When Europe PMC full text is inaccessible, the tool retains the abstract and access status without claiming that the full text was read.
The web tool saves the content, citations, and source URLs actually returned by the API; it does not claim to cache complete web pages.

A live run requires your real sample, a valid API key, explicit live mode, and a budget:

```bash
export OPENAI_API_KEY='your-key'
uv run realclip-d run --input /absolute/path/to/real-sample.json --output runs/live-sample --mode live --budget-usd 1.00
```

`.env.example` only documents the environment variables. The ordinary `realclip-d` CLI **does not automatically read `.env`**. Supply the environment variable through your shell or secret manager. The separate pilot utility below reads its specified credential file only when explicitly running `run` or `complete`.
Live runs incur model and web-search charges; the example budget only illustrates the interface.
Configured token and web-search prices are used for conservative local reservations, not as a bill or a guarantee of final charges. Check the actual model and tool prices before a live run.

Automatic paid-request retries in the SDK are disabled. A request that was sent without a reliable usage receipt retains an unknown status and stops execution rather than being sent again automatically.
A successfully completed research stage can be reused. Resumption checks input and configuration to prevent implicit duplicate paid requests. Observation's reviewed report and Summarize result have separate completion records. If Summarize fails, the completed reviewed report is retained; that failure does not trigger another observation run. All modules share the run's budget ledger. Inspect stage status and saved failure reasons before deciding to start a new run.

## Three-compound research pilot: the first agent only

`realclip_d.research_pilot` researches Nocodazole, Staurosporine, and Rapamycin sequentially, supplying mechanism priors for microtubule destabilization, broad-spectrum protein kinase inhibition, and mTOR inhibition, respectively. The priors remain input claims and still require independent research. New inputs specify `cell_line: "U2OS"`, `dose: null`, and `treatment_duration: null`; no context notes, images, or CP are supplied. Editable inputs for review are in `inputs/research_pilot_u2os/`. The utility invokes only the research stage. Use a new run directory for these revised inputs; existing run records retain their original conditions.

Run inside `D`:

```bash
# Free public interface: resolve PubChem identities and freeze three inputs, configuration, and manifest; no model calls.
uv run python -m realclip_d.research_pilot prepare --run-dir runs/research-pilot-3

# Paid live research: read the user-authorized credential file at the project root.
uv run python -m realclip_d.research_pilot run --run-dir runs/research-pilot-3 --credential-file <PROJECT_ROOT>/.env

# Explicit completion: validate existing candidates locally, then add at most one evidence-synthesis request if necessary.
uv run python -m realclip_d.research_pilot complete --run-dir runs/research-pilot-3 --credential-file <PROJECT_ROOT>/.env

# Read saved local records only; generate or refresh the report during or after a run.
uv run python -m realclip_d.pilot_report --run-dir runs/research-pilot-3
```

`prepare` saves raw PubChem responses and identity-preparation records, freezing each input and its hash. `run` and `complete` verify the frozen inputs and parse only `OPENAI_API_KEY` from the specified `.env`. They do not execute shell content or load other keys. They clear `OPENAI_BASE_URL` and use the official OpenAI API. Credential handling for the ordinary CLI is unchanged.

The three samples share one `budget.json`, capped at **$5** in total. Each research stage permits at most 16 model requests, including at most one synthesis request during explicit completion, for a maximum of 48 requests across the three samples. Completion does not create another allowance. Each request permits at most 12,000 output tokens, including reasoning, and has a conservative local input bound of 250,000 tokens. Requests explicitly use the standard service tier. Reservations use $0.25 per million input tokens, $0.75 per million output tokens, and $0.01 per web search, with at most three searches per request: at most $0.1015 reserved per request and **$4.872** for the full 48-request plan.

These prices support conservative estimates rather than billing. Price sources and frozen configuration are saved in the manifest. Neither the SDK nor the client automatically retries paid requests. Unknown request usage blocks subsequent model calls through the shared ledger. Re-running a command does not automatically resubmit an incomplete paid stage; completed research can be reused.

`complete` is a legacy continuation entry point for saved V2/V3 contracts; it is not part of the current single-run research flow. It first revalidates saved candidates locally. A passing candidate needs no additional model call and its text remains unchanged. Otherwise, it builds a bounded evidence packet from saved evidence the model already saw and makes at most one new synthesis request using the same research-agent prompt. That request has no tools, web search, or new retrieval. It does not resend the full retrieval conversation or introduce raw article text that was not previously shown. It uses the original shared ledger and runs only if all previous usage is known and the original request and budget limits allow it. An existing continuation directory prevents automatic resubmission. Original failure status, requests, and candidates remain preserved.

The first three-compound pilot exposed two issues: Nocodazole and Rapamycin reached the local input guard before final synthesis, so the next request had not been sent; Staurosporine's candidate was rejected by an overly strict check on joint metadata/XML citations for the same paper. The citation rule was corrected locally without changing the model's text. The run report records local revalidation, synthesis completion, and final estimated charges.

`index.html`, `REPORT.md`, and `summary.json` in the run directory show each compound's retrieval timeline, article-access status, evidence, original English hypotheses, verification plans, and budget estimates. Structurally invalid candidates are preserved and labeled. New source-free research uses backend provenance; historical candidates retain their recorded reference-check status. Completion and unknown-usage status are established by the report together with `status.json` / `budget.json`. Report generation makes no retrieval or model requests.

Research tools retain two records: `result` in `tools.jsonl` is the complete tool receipt;
`model_result` is the exact view supplied to the model. `cache/` stores original API
responses. [Article reading](docs/READ_ARTICLE.md) uses overview, selected sections,
or full text with sequential pages, not keyword windows. Retrieval and text
exposure remain distinct from complete reading or comprehension.

[The research agent](docs/RESEARCH_AGENT_SIMPLE.md) uses the original four-stage
prompt and one complete SDK run. The program copies the returned findings and
research gaps unchanged into `findings.json`, without another model call.
Independent notes, memory-query tools and automatic context switching are removed.
Source records remain in backend receipts/caches rather than in the model's output.
New research checks structure and hypothesis/guidance links, without citation-ID,
URL or title gates. Historical output contracts remain readable. The retired
`research_context_bytes` setting is accepted for old configurations but is ignored.

## Concurrent research batches

`realclip-d research-batch --inputs <input-files...> --output <directory> --workers 10`
runs independent complete research agents in a thread pool. Each compound keeps
the approved prompt and its own context and artifacts. The batch shares PubChem
rate limiting and one thread-safe budget ledger. Mock is the default; live requires
an explicit total budget. The observation agent is not run. See
[batch usage and resumption](docs/RESEARCH_BATCH.md).

## Artifacts and test coverage

Each stage saves its input summary, configuration, model requests/responses, tool receipts, usage, status, and structured output.
Research sources, facts, and hypotheses provide traceability. The English
`description` in `observation/result.json` and `observation/description.txt` is the
final short candidate training text. The V5 result also retains `full_description`;
the complete reviewed sentences, observations and CP records remain under
`observation/reviewed/`. The final short text has no evidence-list output or
automatic reference-based rewrite.
Caches, run artifacts, environments, and secret files should not be committed to version control.

Tests cover offline mocks, identity/evidence references, missing CP, corrupt images, rate limits, inaccessible full text, rejected hypotheses, conflicting fields of view, resumption, and replay.
Synthetic mock results test program boundaries. They do not establish retrieval quality, model observation ability, or the biological accuracy of morphological descriptions. Research-pilot outputs also require human review of evidence and inference; consult the corresponding report for completion status.
